# ADR-0005: パーティーマッチングとチーム編成をパーティー単位のチケットで行う

- 状態: 採用
- 日付: 2026-08-23
- 対象: Party Durable Object、Match Pool、Gateway、Client SDK、D1

## 背景

v0.1.0 のマッチングは同じ Pool の 2 枚のチケットを 1 対 1 で成立させるだけで、
パーティー(2 人以上の固定グループ)と 2 対 2 以上のチーム編成は対象外だった
([v0.1.0 Release Note](../releases/v0.1.0.md))。既存の前提は次の通りである。

- チケットは認証主体 1 人の `rating` を持ち、候補探索・確保・成立はすべて
  チケット 2 枚の対で行われる ([match-pool](../match-pool.md))。
- 成立 Room の初期化と試合結果登録は 2 参加者前提で、D1 の参加者履歴は
  `slot IN ('A', 'B')` に固定されている ([ADR-0004](./0004-match-result-trust-boundary.md))。
- Room の状態変更は単調な `revision` と有界イベント履歴で同期し、再開トークンは
  主体・Room・役割へ束縛される ([ADR-0002](./0002-reconnect-and-revision.md))。
- 正本は Durable Object 単位の SQLite であり、識別単位は Room なら `roomId`、
  Match Pool なら `gameId:seasonId:mode:region` である ([ADR-0001](./0001-durable-object-sqlite.md))。

このままチケットへ人数を足すだけだと、メンバーごとの個別チケットが部分成立や
二重確保を起こし、パーティーとしての整合を保てない。

## 決定

### Party Durable Object

1 パーティーを 1 Durable Object(`partyId` 識別)とし、状態の正本を SQLite へ置く。
[ADR-0001](./0001-durable-object-sqlite.md) と同じく、状態変更にはパーティー単位の
単調 `revision` を付ける。Match Pool から独立した識別単位とすることで、どのプールに
も属さないまま招待・編成でき、プール間移動やプール削除の影響を受けない。

すべての状態変更操作には `requestId` を付け、Match Pool の処理済みコマンドと同じ
再生セマンティクスを持たせる。同一 `requestId`・同一 payload・同一主体の再送は
SQLite へ保存した結果をそのまま返す。同一 `requestId` で異なる payload、または別
主体からの再送は `CONFLICT` で拒否する。招待も同じ規則に従い、タイムアウト後の
再送では未使用かつ期限内の既存の単一用途トークンを上書きせずに再利用する。期限
切れまたは使用済みトークンへの再招待だけが新しいトークンを発行する。

状態モデル:

- `members`: 認証主体 ID、役割(`leader` / `member`)、参加時刻。リーダーは常に
  ちょうど 1 人。
- 所属の不変条件: 各認証主体が同時に所属できるパーティーは 1 つだけである。
  作成・参加・招待受諾は対象主体の現在の所属を Party DO 内で原子的に検査し、
  所属済みなら要求全体を拒否する。
- `invites`: 招待先主体 ID、単一用途トークン、有効期限。期限切れと使用済みは
  無効化する。同一主体への重複招待は前項の再生規則に従い、未使用かつ期限内の
  トークンを保持し、期限切れ・使用済みのときだけ再発行する。
- 定員は Pool 設定とは独立に `maxPartySize` で制限する。

解散ポリシー:

- リーダーの明示的な解散操作で解散する。
- リーダーが自発的に退出した場合は解散せず、最古参メンバーへ権限を移譲する。
- メンバー数が 2 未満に減った時点で自動解散する。
- 切断猶予は適用しない。ロビー段階のグループであり、Room と違って離脱意思が
  曖昧にならないためである。無活動パーティーは Alarm + TTL で掃除する。

### Match Pool チケットの N 人拡張

チケットを「参加者集合」の単位へ拡張する。

- チケットは `memberIds`(ソート済み・重複なし)、`partyId`、キュー投入時点の
  `partyRevision` スナップショットを持ち、対応する Party Durable Object を明示的
  に参照する。チケットの所有者はリーダーであり、作成はリーダーだけが行う。
  メンバー個別のチケットは存在しない。
- キュー投入時に Party DO の現在 `revision` とスナップショットの一致を検証し、
  メンバーシップを凍結する。待機中のチケットが存在する間、Party DO は参加・
  退出・招待受諾などの構成変更を拒否し、解散はチケットのキャンセルを伴う。
  これにより古い `memberIds` のまま確保が進むことを防ぐ。
- Pool 設定に `maxPartySize`(既定 1、1 の場合は v0.1.0 と完全互換)と、各チームの
  人数 `teamSize`(既定 1)を追加し、チケットあたりの人数上限を宣言的に制限する。
- キュー投入時は全 `memberIds` について有効な待機チケットの有無を原子的に検査し、
  1 人でも既にキューにいる主体がいれば N 人分の投入を一括で拒否する。これにより
  パーティー経由の二重キュー投入を防ぐ。
- 対戦 Room の初期化は、チケットの `memberIds` 全員を同一チームへ割り当てて
  行う。チーム割り当てはパーティー単位であり、パーティーをまたいだ混成は
  行わない。チーム ID は Pool の `teamIds` を使い、チーム内メンバーの順序は
  ソート済みの `memberIds` で確定するため、試合結果登録の再生でも同じチーム ID
  とメンバー順序が再現できる。
- 候補探索は構成人員が `teamSize` と一致しないチケット、および構成人員が異なる
  チケット同士の組を成立不可として評価段階で拒否する。人数不一致の試合は許可
  しない。

### 探索幅とレーティング参照値

- レーティング参照値は、キュー投入時にスナップショットしたメンバーレートの
  算術平均とする。整数化が必要な場面では ELO の差分と同じ「0.5 はゼロから遠い
  方向へ丸める」規則を使い、レートが非負のため実質的に切り上げになる。以降の
  待機中はスナップショットを参照し、待機中のレート変動は追跡しない。
- 検索幅の段階拡張(既定 75 → 150 → 400)は変更せず、この平均値に対して適用する。
- 候補品質は既存の決定論的評価契約 (`compareMatchCandidateQuality`) へ最大構成員
  偏差を挿入した優先順位で比較する。比較はすべて丸め前の実数値で行い、小さい
  ほど優先する:

  1. チケット間の平均レート差(昇順)
  2. 入力方式の一致
  3. チケット内の最大構成員偏差(昇順。丸め前の平均と実メンバー値の差)
  4. 最長待機時間(降順)、次に最新待機時間(降順)
  5. 候補 ID の辞書順(完全同値時の最終 Tie Break)

  これにより平均が近くても偏った編成の成立を避ける。

### `revision` と再開トークンとの整合

[ADR-0002](./0002-reconnect-and-revision.md) と同じ契約を Party とパーティー
チケットへ適用する。

- Party DO のイベントはパーティー単位の `sequence` を持ち、クライアントは
  差分適用、欠落・逆順時に Snapshot 再同期へ切り替える。履歴は有界とする。
  イベント接続はリーダーに限らずメンバー全員が自分の主体で開け、Party DO が
  接続主体のメンバーシップを検証する。
- マッチングチケットの進捗(waiting / matched / cancelled)は、Pool 全体の
  `sequence` 採番を流用した既存の通知形式のまま Match Pool から Party DO へ
  転送され、Party DO がパーティー単位の購読経由でメンバー全員へ配信する。
  非リーダーの進捗購読はチケットの所有とは独立しており、成立・キャンセル・
  期限切れで購読を解除する。解除後の状態取得は最終 Snapshot で行う。
- 成立後の対戦 Room の再開トークンは引き続き個人主体へ束縛する。パーティー単位の
  共有トークンは発行しない。パーティー脱退済み主体の参加は Room 側の役割検証が
  拒否する。

### D1 スキーマ変更

`migrations/` への新ファイル追加のみを行い、既存テーブルの列追加や CHECK 制約の
変更はしない。

- チーム対応の試合結果は新しいテーブル群(チーム単位の試合テーブルと、
  `slot IN ('A', 'B')` を一般化した参加者テーブル)として追加する。1 対 1 の
  既存テーブルと [ADR-0004](./0004-match-result-trust-boundary.md) の API 契約は
  温存し、既存データの移行は不要とする。
- パーティーの正本は Party DO SQLite であり、D1 へ投影しない。検索需要が生じた
  場合は [ADR-0003](./0003-public-room-index.md) と同じ非同期投影の型で後続
  Issue で扱う。

## 代替案

- メンバーごとに個別チケットを作り、探索時に同一パーティーへ合流させる:
  部分的な確保と、合流タイミングでの不整合が起こるため不採用。
- パーティーの参照レートを最低レート構成員に合わせる: 高レート帯の待機が
  極端に伸び、サンドバッギングを招くため不採用。平均 + 最大偏差の Tie Break で
  偏った編成を緩和する。
- 最高レート構成員に合わせる: 低レート帯が高レート帯へ連れて行かれるため不採用。
- パーティー状態を Match Pool DO 内へ置く: プール横断で利用できず、プール設定の
  変更でパーティーが失われる。[ADR-0001](./0001-durable-object-sqlite.md) の
  識別単位の分離に反するため不採用。
- パーティー単位の再開トークンを発行する: 一人だけが残った状態でもトークンが
  有効になり、退場済み主体のなりすましと権限の混乱を許すため不採用。
- 既存の rating 系テーブルへ列を足す、CHECK 制約を緩める形のインプレース移行:
  公開済み schema の破壊的変更となり、失敗時のロールバックができないため不採用。
- 切断猶予をパーティーへも適用する: Room と異なり離脱が明示的操作で表現できる
  ため不採用。

## 後続 Issue への分割線

実装は次の順序で分割する。各段は前段の公開型・API が固定された後に着手する。

1. **core**: `MatchmakingSearchTicket` の参加者集合拡張、N 人チケットの候補評価と
   品質比較、`maxPartySize` を含む Pool 型拡張。依存なし。
2. **cloudflare**: Party Durable Object、Match Pool の N 人チケット対応、Gateway
   エンドポイント、`migrations/` へのチーム試合テーブル追加、統合テスト。
   core の型固定が前提。
3. **client**: パーティー作成・招待・退出、リーダーによるキュー参加、進捗と
   チーム編成の表示。cloudflare の HTTP/WebSocket 契約が固定された後に着手。

## 結果

パーティーは Match Pool から独立した正本を持ち、チケットは参加者集合を 1 単位と
して扱うため、部分成立や二重確保なく 2 対 2 以上のマッチングへ拡張できる。
参照レートを平均へ寄せることで、既存の検索幅ポリシーと ELO を変更せずに再利用
できる。一方で、チケット 1 件が複数主体を束縛するため、キャンセル・期限切れの
影響がメンバー全員へ及ぶこと、Party DO という新しい識別単位の運用が増えること
を受け入れる。1 対 1 の既存経路は `maxPartySize` 既定値 1 により挙動を変えない。
