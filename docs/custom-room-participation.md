# カスタムルームの参加・退出・観戦

カスタムルームの作成後は、Gateway Worker の参加 API からプレイヤーまたは観戦者として参加できます。最終的な参加可否と定員判定は、対象 `roomId` の Room Durable Object が SQLite の現在状態を根拠に決定します。

## 参加

`POST /v1/custom-rooms/join` に次のいずれかを指定します。

```json
{
  "requestId": "join-request-1",
  "roomId": "room_xxx",
  "role": "player",
  "password": "必要な場合だけ"
}
```

招待方式では `roomId` の代わりに `invitationCode` を指定できます。URL の `/v1/custom-rooms/{roomId}/join` または `/v1/custom-rooms/{invitationCode}/join` も利用できます。`role` は `player` が既定値で、観戦時は `spectator` を指定します。

作成者の初期参加と、後続の参加成功では、対象ルーム・認証主体・役割・参加者識別子・有効期限を束縛した参加用トークンが返ります。トークンはクライアントが任意の `playerId` を申告するためには使用できません。

参加方式ごとの確認は次のとおりです。

- `public`: 認証と認可を通過すれば参加できます。
- `invitation`: 招待コードが D1 の索引と Room Durable Object の両方で一致する必要があります。
- `password`: パスワードは平文保存せず、Room Durable Object 内でソルト付きハッシュと照合します。

プレイヤーと観戦者の定員は別々に数えます。同じ主体による同じ役割の再送は既存の参加者情報を返しますが、別の役割での重複参加は競合として拒否します。

## 退出と通信切断

`POST /v1/custom-rooms/leave` に `roomId`、参加用トークン、任意の `participantId` と `role` を指定します。トークンを検証した後、所有者本人の参加者行だけを削除します。削除時に参加枠が空き、プレイヤーの準備状態とチーム所属も失われるため、再参加時は新しい参加者として初期状態から始まります。

同じ `requestId` の退出再送は保存済み結果を返します。WebSocket の一時的な通信切断は `RoomDurableObject.disconnect()` を利用し、参加者行やリビジョンを変更しません。明示的なホスト退出では、最も古いプレイヤーへホストを移譲し、移譲先がなければルームを閉鎖します。通信切断だけではホスト移譲を行いません。

## 検証

カスタムルーム統合テストでは、公開・招待・パスワード・観戦の正常系、役割別の定員、同時参加、重複要求、誤った認証情報、退出後の再参加、通信切断の保持を確認します。参加用トークンの期限、用途、主体、ルーム、役割、署名はセキュリティテストで検証します。
